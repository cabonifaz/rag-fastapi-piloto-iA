# VLM Workflow Plan

Plan for implementing a Vision Language Model (VLM) workflow based on the existing RAG LangGraph architecture, replacing vector DB search with direct image+text inference.

---

## How the Existing RAG Workflow Works

The workflow is a LangGraph `StateGraph` — a directed graph where each node is an async function that reads from and mutates a shared `RAGState` TypedDict. There's no global mutable state between requests; each invocation gets its own state dict passed node-to-node.

### Node Pipeline (in order)

```
validate_inputs
    │ (stop if invalid)
    ▼
get_conversation_history  ← fetches from message service (DynamoDB/DB)
    ▼
clean_message             ← sanitizes input text
    ▼
context_gatekeeper        ← LLM call: does this query need conversation context?
    │
    ├── needs_context=True  → recontextualize_query  ← rewrites query with history
    │                              │
    └── skip ─────────────────────┘
                                   ▼
                            load_rag_config          ← fetches LLM/RAG config from DB
                                   ▼
                            create_or_use_chat       ← creates or reuses a chat session
                                   │ (stop if error)
                                   ▼
                            save_user_message        ← persists user message
                                   │ (stop if error)
                                   ▼
                            determine_query_for_search  ← picks: recontextualized or original
                                   ▼
                            generate_embedding          ← embeds the query
                                   ▼
                            search_vector_db            ← retrieves relevant chunks
                                   ▼
                            build_context               ← concatenates chunks into context_text
                                   ▼
                            select_history_for_prompt   ← trims conversation history
                                   ▼
                            build_rag_prompt            ← assembles final text prompt
                                   ▼
                            prepare_timestamps
                                   ▼
                                  END
```

After the graph finishes, `stream_llm_response()` (called by the endpoint, **outside** the graph) takes the final `state` and actually calls the LLM with the assembled prompt.

---

## VLM Workflow Design

For the VLM version the whole vector search branch is **removed** and replaced with a node that builds a **multimodal prompt** (text + one or more image S3 keys). Files are uploaded to S3 by the frontend **before** the VLM query is sent. Their S3 keys are passed in as initial state and used directly by the Bedrock Converse provider via `s3Location` — no presigned GET URLs needed for the LLM call.

A message can carry **zero or more attachments** — the design handles all cases uniformly via a list.

### What changes vs the RAG workflow

| RAG workflow | VLM workflow |
|---|---|
| `determine_query_for_search` | removed |
| `generate_embedding` | removed |
| `search_vector_db` | removed |
| `build_context` | removed |
| `build_rag_prompt` | → `build_vlm_prompt` (multimodal) |
| state: `query_embedding`, `search_results`, `context_text`, `query_for_search` | removed |
| state: `attachment_keys` | added |

## File Upload Flow

### Frontend flow (on press send)

```
User presses send (message + files selected)
  │
  ├─ POST /vlm/upload-urls
  │    { filenames: ["img1.png", "img2.jpg"] }
  │    ← { timestamp: "1741123456789", uploads: [{ presigned_url, s3_key, filename }] }
  │
  ├─ PUT {presigned_url}  ×N  (parallel, direct to S3 — backend not involved)
  │    ← 200 from S3
  │
  └─ POST /vlm/query
       { message, attachment_keys: ["attachments/42/1741.../img1.png", ...], ... }
       ← SSE stream
```

### S3 key format

```
attachments/{user_id}/{timestamp}/{filename}
```

- `user_id` is always known (JWT); no `chat_id` needed at upload time.
- `timestamp` is generated by the backend at `/vlm/upload-urls` time — consistent and trustworthy.
- Bucket: `S3_PDFS_BUCKET` (from env).

### Orphaned file cleanup

If the user aborts after uploading but before sending the query, the files remain in S3. These are cleaned automatically by an **S3 Lifecycle rule**:

```
Prefix: attachments/
Action: delete after 1 day
```

Files that make it into a DynamoDB message are effectively permanent (referenced); orphaned ones are removed within 24 h at negligible cost.

## Implementation

### 1. New `VLMState` — `app/workflows/states.py`

```python
class VLMState(TypedDict):
    # Input parameters
    user_id: int
    message: str
    company_id: int
    area_id: int
    created_at: str
    chat_id: Optional[str]
    request_timezone: Optional[str]
    attachment_keys: List[str]   # S3 keys — stored permanently in DynamoDB + used in Bedrock s3Location

    # Processing state
    cleaned_message: Optional[str]
    conversation_history: List[Dict[str, str]]
    gatekeeper_result: Dict[str, bool]
    recontextualized_query: Optional[str]
    rag_config: Optional[Dict[str, Any]]
    new_chat_created: bool
    new_chat_titulo: Optional[str]
    new_chat_timestamp: Optional[str]
    conversation_history_for_prompt: List[Dict[str, str]]
    vlm_prompt: Optional[Any]   # multimodal content list built from attachment_keys
    assistant_timestamp: Optional[str]
    assistant_timestamp_ms: Optional[int]
    utc_formatted: Optional[str]
    local_formatted: Optional[str]

    # Error handling
    error: Optional[str]
    should_stop: bool
```

### 2. New node: `create_build_vlm_prompt_node` — `app/workflows/nodes/prompt_nodes.py`

The node stores the cleaned message and attachment keys into `vlm_prompt`. The actual Bedrock `s3Location` blocks are built later by `AWSBedrockVLMProvider._build_image_block()` at call time.

```python
def create_build_vlm_prompt_node():
    async def build_vlm_prompt(state: VLMState) -> VLMState:
        state["vlm_prompt"] = {
            "message": state["cleaned_message"],
            "attachment_keys": state.get("attachment_keys") or [],
        }
        return state
    return build_vlm_prompt
```

### 3. New workflow file — `app/workflows/vlm_workflow.py`


### 4. Streaming helper — `app/workflows/helpers/streaming_helpers.py`

```python
async def stream_vlm_response(state, vlm_provider, message_service, db):
    rag_config  = state["rag_config"]
    vlm_prompt  = state["vlm_prompt"]   # { message, attachment_keys }
    messages    = state.get("conversation_history_for_prompt") or None

    async for chunk in vlm_provider.generate_stream(
        model_id=rag_config['config']['LLM_MODEL'],
        message=vlm_prompt["message"],
        attachment_keys=vlm_prompt["attachment_keys"],
        max_tokens=rag_config['config']['LLM_MAX_TOKENS'],
        temperature=rag_config['config']['LLM_TEMPERATURE'],
        top_p=rag_config['config']['LLM_TOP_P'],
        role_behavior=rag_config['config']['ROLE_BEHAVIOR'],
        messages=messages,
        request_timezone=state.get("request_timezone"),
        utc_formatted=state.get("utc_formatted"),
        local_formatted=state.get("local_formatted"),
    ):
        yield chunk
```

## API Endpoints

### `POST /vlm/upload-urls`

Generates presigned PUT URLs for direct S3 upload by the frontend.

**Request:**
```json
{ "filenames": ["img1.png", "img2.jpg"] }
```

**Response:**
```json
{
  "timestamp": "1741123456789",
  "uploads": [
    { "presigned_url": "https://s3...", "s3_key": "attachments/42/1741123456789/img1.png", "filename": "img1.png" },
    { "presigned_url": "https://s3...", "s3_key": "attachments/42/1741123456789/img2.jpg", "filename": "img2.jpg" }
  ]
}
```

- `user_id` taken from JWT — not sent by client.
- `timestamp` generated by backend — same value used in all S3 keys.

### `POST /vlm/query`

Runs the VLM workflow and streams the response.

**Request (JSON):**
```json
{
  "message": "What do you see in these images?",
  "attachment_keys": ["attachments/42/1741123456789/img1.png"],
  "chat_id": null,
  "area_id": 3,
  "created_at": "1741123456789",
  "request_timezone": "America/Bogota"
}
```

**Response:** SSE stream of text chunks.

### DynamoDB message item (user message with attachments)

```json
{
  "chat_id": "chat-5",
  "created_at": "1741123456789",
  "sender": 0,
  "message": "What do you see in these images?",
  "attachment_keys": ["attachments/42/1741123456789/img1.png", "attachments/42/1741123456789/img2.jpg"],
  "id_estado_registro": 1,
  "chat_id#id_estado_registro": "chat-5#1"
}
```

Messages without attachments simply omit `attachment_keys` — no schema change needed.

When the message read path returns messages, the service layer generates fresh presigned GET URLs (`ExpiresIn=60`) from the stored `attachment_keys` and appends them as `attachment_urls: List[str]` in the response.
