Context Detection Rules
needs_context Decision Matrix

needs_context → true if query references previous interaction or conversation history

context_messages Calculation Rules

Primary Indicators (based on explicit scope):
Single Message Reference (references to one specific previous message) → 1

Multiple Messages Reference (references to several recent messages) → 2-4

Summary/Overview Request (requests to summarize or overview conversation) → 10-12

Specific Topic Continuation (continues specific previously discussed topic) → 5-7

General Conversation Reference (general references to past discussion) → 5

Grammatical Precision Rules:
Singular references (uses singular form for message/conversation) → 1

Plural references (uses plural form for messages/conversations) → 2-4

Quantified references (specifies exact number of messages) → use exact number mentioned

Ambiguous references (vague references without clear scope) → 2

Decision Hierarchy:
First priority: Quantified references (use exact number)

Second priority: Singular/Plural grammatical indicators

Third priority: Reference type categories

Default: 2 for ambiguous cases

System Data Rules
needs_system_data → true only if the query requires internal data and mentions one or more columns that exist in an endpoint's "Columns" list from the API list.

system_calls → include one entry only for endpoints whose columns match the query:

entity = descriptive name of the entity

endpoint = API endpoint path

method = GET or POST

params = object containing only explicitly provided parameters from the query

missing_required_params = array of required parameters that are missing from the query

DO NOT INFER PARAMETERS - only use parameters explicitly provided in the query

If required parameters are missing, include them in missing_required_params

External Knowledge Rules
needs_external_knowledge → true if the query requires external knowledge retrieval

semantic_query → preserve the original language and wording

Combined Source Detection Rules
When to set BOTH needs_system_data AND needs_external_knowledge to true:

Comparative Analysis Queries

Comparing system data with external standards/best practices

Example: "Compare our current routers with industry best practices"

Validation/Compliance Queries

Checking if system data meets external standards

Example: "Verify if our network setup follows security guidelines"

Enhanced Recommendation Queries

Using system data + external knowledge for recommendations

Hybrid Research Queries

Combining internal metrics with external benchmarking

Example: "Show our transaction volume compared to market averages"

Query Analysis Priority:

First, detect if system data is needed (internal metrics, current state)

Then, detect if external knowledge is needed (standards, best practices, general knowledge)

Set both to true if query clearly requires both information types

Format Detection Rules
format → "table" if query contains "table" or "tabla"

format → "list" if query contains "list", "lista" OR ordering words

format → null in other cases

Table Word Disambiguation Rule
If "table"/"tabla" appears in a context-related query (resume, summary, conversation) → treat as format indicator only

If "table"/"tabla" appears with system data terms (switches, routers, users, orders) → treat as potential system data reference

Default: assume format indicator unless clear system entity is mentioned

Other Rules
query_clean → always include original query text

JSON must be valid and complete
